学习 STM32 的 UART、SPI 和 I²C 时，经常遇到同步、异步、全双工、半双工、串行、并行等术语。再加上大端、小端和高低位先发，很容易把它们混在一起。

这些概念分别回答不同的问题。理解时，可以先看它到底在描述**采样时刻、通信方向、数据通道，还是数据排列顺序**。

## 1. 同步与异步：接收方什么时候采样？

发送方把电平输出到线上，接收方需要在合适的时刻读取。过早或过晚采样，都可能把数据读错。

### 同步通信

在常见的 STM32 板级接口中，同步通信通常使用配套的时钟信号，让双方根据时钟确定数据采样时刻。

例如 SPI 的 SCK、I²C 的 SCL。时钟和数据各有信号线，接收方按协议规定的时序读取数据。

这里的“同步”指通信时序有共同依据，并不意味着两边的程序每一步都同时执行。更广义的同步通信还可能从数据信号中恢复时钟，因此不能把“有独立时钟线”当成所有通信系统的统一定义。

### 异步通信

常见 UART 通信没有单独传输的时钟线。双方提前约定波特率、数据位数、校验方式和停止位等参数，接收方根据起始位确定一帧的接收时机，再用本地时钟采样。

以 8N1 为例，一帧通常包含：

```text
起始位 | 8 个数据位 | 1 个停止位
  1 位       8 位          1 位
```

8N1 中，`8` 是数据位数，`N` 表示无奇偶校验，`1` 表示一个停止位。

**异步通信仍然需要时序。** 双方波特率偏差过大，同样会导致接收错误。

还要区分硬件通信与软件调用中的术语：程序里的同步调用、异步调用，讨论的是操作完成、返回和结果通知的关系，不是在判断有没有通信时钟线。

## 2. 单工、半双工与全双工：能否同时收发？

这一组概念关注的是传输方向，以及两个方向能否同时工作。

| 方式 | 传输能力 | 便于理解的类比 |
| --- | --- | --- |
| 单工 | 只能沿一个方向传输 | 广播台向收音机发送 |
| 半双工 | 可以双向传输，但需要轮流发送 | 对讲机 |
| 全双工 | 可以同时发送和接收 | 电话通话 |

注意，“支持双向通信”只说明两边都能发，还不能据此判断它是不是全双工。

### UART 为什么通常是全双工？

使用独立 TX、RX 引脚时，一条路径负责发送，另一条路径负责接收，两个方向可以同时工作。

```text
设备 A 的 TX ─────→ 设备 B 的 RX
设备 A 的 RX ←───── 设备 B 的 TX
```

这是逻辑数据连接示意；实际接线还要满足参考地、电平和接口电气要求。

### I²C 为什么是半双工？

I²C 的读写数据共用 SDA，同一时刻不能在这根线上传输两组独立的双向数据，因此数据传输属于半双工。SCL 是时钟线，不是另一个方向的数据线。

### SPI 为什么通常是全双工？

常见 SPI 使用独立的 MOSI 和 MISO，两条数据路径可以在同一组时钟下同时移位。

但外设支持全双工，不等于每次交易两个方向都有有效业务数据。读寄存器时，控制器可能需要发送占位数据来产生时钟。

这些分类都需要结合具体模式：部分 MCU 支持单线半双工 UART，SPI 也可能工作在半双工或单向模式。判断时应看实际配置和接线。

## 3. 串行与并行：多个数据位怎么通过接口？

- **串行**：在一条数据路径上，数据位按时间先后依次传输。
- **并行**：使用多条数据线，在同一传输时刻传输多个数据位。

以发送四位数据 `1011` 为例：

```text
串行：一条数据路径，先后传 1 → 0 → 1 → 1
并行：四条数据线，在同一时刻分别表示 1、0、1、1
```

UART、常见 SPI 和 I²C 都属于串行通信。SPI 同时使用 MOSI、MISO，并不使它变成并行接口：它们分别承担两个方向的串行数据。

串行也不必然比并行慢。实际吞吐量还受时钟频率、通道数量、编码和协议开销影响。

## 4. 把 UART、SPI、I²C 放在同一张表里

| 常见接口形式 | 同步方式 | 双工方式 | 数据传输方式 |
| --- | --- | --- | --- |
| UART，独立 TX/RX | 异步 | 全双工 | 串行 |
| SPI，独立 MOSI/MISO | 同步 | 全双工 | 串行 |
| I²C，共用 SDA | 同步 | 半双工 | 串行 |

这张表描述常见使用形式，而不是所有硬件模式。USART 名称中的 `S` 表示它还支持同步通信，不能因为平时把它配置成 UART 使用，就认为这个外设只支持异步模式。

## 5. 大端与小端：多字节数据怎样放进内存？

先区分两个单位：

- **位（bit）**：一个二进制位，取值为 0 或 1。
- **字节（byte）**：在本文涉及的 STM32 环境中，一个字节包含 8 位。

一个 `uint32_t` 占四个字节。对于数值 `0x12345678`，可以把它拆成：

```text
高有效字节                              低有效字节
   0x12         0x34         0x56         0x78
```

这里的“高”“低”指字节在**数值中的权重**，还没有涉及它放在哪个地址。

假设这个变量从内存地址 `0x20000000` 开始存放：

| 内存地址，从低到高 | 大端存储 | 小端存储 |
| --- | --- | --- |
| `0x20000000` | `0x12` | `0x78` |
| `0x20000001` | `0x34` | `0x56` |
| `0x20000002` | `0x56` | `0x34` |
| `0x20000003` | `0x78` | `0x12` |

- **大端（Big-endian）**：高有效字节放在低地址。
- **小端（Little-endian）**：低有效字节放在低地址。

两种布局表示的数值都是 `0x12345678`。变化的是内存中的字节排列，数值本身没有反转。

单独一个字节不存在这种多字节排列问题；它内部各位的发送顺序属于下一节的“位序”。

## 6. 字节序和位序：不要把两种顺序混在一起

讨论通信时，最好把两个问题分别问清楚：

1. 一个多字节数，先传高字节还是低字节？这是协议中的**字节顺序**。
2. 每个字节里面，先传最高有效位还是最低有效位？这是**位序**。

以单字节 `0x96` 为例：

```text
二进制书写：b7 b6 b5 b4 b3 b2 b1 b0
            1  0  0  1  0  1  1  0

MSB first： 1 → 0 → 0 → 1 → 0 → 1 → 1 → 0
LSB first： 0 → 1 → 1 → 0 → 1 → 0 → 0 → 1
```

MSB 是最高有效位，LSB 是最低有效位。这里展示的是数据位，不包括起始位、校验位或停止位。

常见 UART 以 LSB first 发送一个字符的数据位，但这**不能决定一个 16 位数的两个字节谁先发送**。

例如用常见 8 位 UART 帧传输 `0x1234`：

| 协议约定 | 第一个数据字节 | 第二个数据字节 | 每个字节内部 |
| --- | --- | --- | --- |
| 高字节先传 | `0x12` | `0x34` | 都按 UART 配置发送各数据位 |
| 低字节先传 | `0x34` | `0x12` | 都按 UART 配置发送各数据位 |

因此，同一个采用 LSB first 的 UART，可以承载高字节先传的协议，也可以承载低字节先传的协议。不能用“UART 低位先发”来推断整个数据包的字节序。

## 7. STM32 串口打包：明确规定字节顺序

假设需要发送一个 16 位数值 `0x1234`。与其依赖变量在内存里的排列，不如按照协议显式拆分。

### 高字节先传

```c
#include <stdint.h>

uint16_t value = 0x1234;

uint8_t tx[2] = {
    (uint8_t)(value >> 8),
    (uint8_t)(value & 0xFFu)
};
// 按 tx[0]、tx[1] 的顺序发送：12 34
```

接收端按同样的约定组合：

```c
uint16_t result = (uint16_t)(
    ((uint32_t)rx[0] << 8) | (uint32_t)rx[1]
);
```

### 低字节先传

```c
uint8_t tx[2] = {
    (uint8_t)(value & 0xFFu),
    (uint8_t)(value >> 8)
};
// 按 tx[0]、tx[1] 的顺序发送：34 12
```

对应的组合方式：

```c
uint16_t result = (uint16_t)(
    ((uint32_t)rx[1] << 8) | (uint32_t)rx[0]
);
```

这里假设 `rx` 是已经接收到完整两个字节的 `uint8_t` 数组；代码展示的是数值编解码，不包含收包、长度检查和校验逻辑。

显式移位与掩码可以让协议顺序独立于主机的内存字节序。直接把整数或结构体的内存当作数据包发送，则还要考虑字节序、结构体填充和数据类型表示等问题。

还要区分**原始字节与文本**：发送 `0x12`、`0x34` 两个原始字节，和发送字符串 `"1234"` 不一样。后者按 ASCII 编码是 `0x31 0x32 0x33 0x34` 四个字节。

## 8. 还有哪些容易一起出现的概念？

| 概念 | 主要回答的问题 |
| --- | --- |
| 波特率 / 比特率 | 每秒传多少个符号 / 每秒传多少个二进制位？ |
| 单端 / 差分 | 按相对参考地的电压，还是两根线的电压差判断信号？ |
| 点对点 / 总线 | 连接两个通信端，还是让多个设备共享通道？ |
| 轮询 / 中断 / DMA | 处理器怎样获知收发状态、怎样搬运数据？ |

例如，UART 配置为 115200 baud、8N1 时，在连续无间隙发送的理想情况下，每个有效数据字节需要占用 10 个比特时间，单方向有效数据速率约为：

```text
115200 ÷ (1 + 8 + 1) = 11520 字节/秒
```

因此，115200 不是每秒发送 115200 个有效数据字节。协议头、校验字段和帧间停顿还会进一步影响实际业务吞吐量。

轮询、中断和 DMA 则是另一层的实现选择。UART 从轮询收发改成 DMA 收发后，它的异步、串行等接口属性不会因此改变。

## 9. 调试通信时，可以按这个顺序检查

1. **电气连接**：电平是否兼容，参考地是否正确，收发线和时钟线是否接对。
2. **通信时序**：UART 的波特率、帧格式是否一致；SPI 的时钟极性、相位等是否匹配。
3. **通信方向**：接口是否需要切换收发方向，是否存在总线冲突。
4. **位序与字节序**：每个数据单元怎样移位，多字节字段按什么顺序排列。
5. **协议内容**：帧头、长度、校验、数值类型和编码是否一致。

如果串口助手中收到的是 `34 12`，而预期是 `12 34`，应先检查程序的打包顺序；如果字符普遍乱码，则要先检查电气条件、波特率和帧格式。先定位问题属于哪一层，再决定修改哪一处配置。
